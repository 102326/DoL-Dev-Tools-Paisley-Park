# DoL Dev Tools project rules

- Read [.agents/skills/dol-dev-tools-paisley-park/SKILL.md](.agents/skills/dol-dev-tools-paisley-park/SKILL.md) and only the relevant command/architecture documents before work. Keep this file short; the Skill owns detailed workflows.
- For human-facing documentation, repository memory/archive or release preparation, follow [auxiliary Skill and delivery rules](docs/AUXILIARY_SKILLS.md). Use existing writing Skills as needed, preserve facts/Unknown, and inspect the release file list; do not auto-migrate directories or add a parallel execution system.
- Define scoped Done from the task: deliverables, required behavior, acceptance environments, material risks and completion conditions. Do not add exhaustive ecosystem acceptance at the end.
- Match validation to actual risk. Documentation-only changes need link, instruction-consistency and format checks; behavior changes need affected tests and representative integration/device evidence as warranted. Explain the unresolved risk before escalating. Reuse valid unaffected evidence; do not test more merely because more tests are possible.
- Distinguish Completed, Implemented/coverage limited and Not implemented. Untested environments do not mean unfinished implementation. Optional/Future coverage belongs in the [current Coverage Ledger](docs/CLOSEOUT_6_1.md#coverage-ledger), not automatically in Remaining work; promote only for explicit user/release requirements, risk evidence or a real issue.
- Balance reuse, innovation and necessary refactoring. Reuse verified Android/CDP/ADB/Evidence/Action/Journey and target workflows; design missing Gameplay orchestration, planning, Scene/Memory and recovery when needed. Replace obstructive internal structures instead of adding endless glue; explain the problem, preserved capabilities and migration. See [historical 3.0 architecture audit](https://github.com/102326/DoL-Dev-Tools-Paisley-Park/blob/cf405fdf132468a8ca9dbb8a3a2c7efbf8e874b1/docs/GOLD_EXPERIENCE_REAUDIT.md).
- Android CLI shows the device screen; Chrome Inspect/CDP connects agents to the live WebView; ADB exposes Android/App system state. Generic Diagnostics must work without any particular Mod or Runtime. Missing, unsupported or failed Optional Integrations must not invalidate successful Generic collection.
- Integration code must be reviewed local code. Workers isolate faults, not Node file/network permissions; they are not security sandboxes. Evaluators execute supplied JavaScript; read-only is a Probe/workflow rule, not an evaluator permission boundary.
- Keep Android/CDP/DOM observations separate from Runtime/Adapter/Integration interpretations. Do not infer compatibility failure from pixels, leaks from memory growth or WebView recreation from PID changes; unknown is not failure.
- Evidence complete/partial/failed describes a capture, not product completion. Preserve failures and proof limits. Reports separate Delivered, Validated, Not validated and Known limitations; Remaining work contains only actual in-scope implementation/fix needs.
- Absorb field feedback by checking existing rules, deduplicating, extracting decision lessons and recording cases/candidates. Strengthen an existing rule before adding another; keep project details out of the generic Skill. Feedback alone does not authorize refactoring, new coverage or a release.
- For current-version Mod research, check the author's latest release and obtain an isolated package when the task needs its contents. Explicit historical/reproduction tasks keep the reviewed fixed input, state its relationship to current versions and do not require an unrelated latest-package download. Pin sources and package digests; distinguish research input from the version actually loaded. Update an authorized test target with backups and loaded-result checks, preserving older evidence under its original version.
- Preserve unrelated edits and evidence. At the user's explicit request on 2026-10-08, the 3.0 development chain was squashed onto v2.0.1; v3.0.0/v3.0.1 releases and tags were removed, and v3.0.2 was rebound to the reset history. Current Gold Experience Requiem acceptance is in [closeout](docs/CLOSEOUT_3_0_3.md). Historical validation records remain evidence, not current download instructions. Future history rewrites require corresponding user scope. Publish only after acceptance; never upload private game evidence, resources, saves or credentials.
