# DoL Dev Tools: Paisley Park 3.0 — Gold Experience 设计审计

日期：2026-10-06。审计基线：Paisley Park 2.0.1，提交 `7c2b975b30338755a34aa61515c8b47efb59875b`。

**当前状态：正式v3.0.0已撤回，现有成果保留为Foundation；最新目标与设计见[架构重新审计](GOLD_EXPERIENCE_REAUDIT.md)。** 本文保留初版审计与阶段记录，原A—D证明有效但不足以代表新的正式Gold Experience。原“只允许薄层/不引入Agent框架”等限制已被用户新要求取代：能复用就复用、缺核心就设计、旧结构阻碍就重构。下方历史完成/Remaining work不代替最新状态；已有接口以[GAMEPLAY](GAMEPLAY.md)为准。

最初设计审计的Done：核对现有执行、观察、Integration、Evidence和Skill边界，给出最小能力模型、复用关系、状态读取、动作映射、安全模型与首批真实用例。该阶段仅交付文档；后续实施已开始，状态单独记录。新的总原则是：正常Gameplay默认自治，删除/覆盖已有存档默认禁止；目标驱动动态重规划，Journey只是一种执行手段。

## 1. 结论与现有能力审计

建议新增一层薄的Game Semantic / Gameplay Agent Layer：读取当前原状态，解释一组有限语义，为下一个动作生成受约束的执行片段，复用现有Action/Journey，随后重新读取原状态判断目标。开发验收和gameplay共用这一层；任务目的影响证据与断言，不改变业务真相源或安全权限。

当前Tools有执行与诊断基础设施，**没有自有DoL业务Runtime**。Soft & Wet的UI Runtime属于目标项目；3.0不将它搬进Tools，也不以安装它为前提。

| 已核对路径 | 可直接复用 | 当前缺口 / 不应误认 |
| --- | --- | --- |
| [Action](../scripts/lib/action.cjs) | 固定动作校验、明确设备/package/user、前台/焦点检查、原DOM click/input、生命周期动作 | 不理解商品/服装/金额；`web-click`为`node.click()`，不检查中心遮挡，不证明真实触摸或trusted事件 |
| [Journey](../scripts/lib/journey.cjs) | 静态plan、顺序执行、wait/checkpoint、50步/120秒上限、失败停止、已派发结果unknown、资源清理 | 没有业务状态assert、语义目标、动态条件分支或外部可恢复执行协议；checkpoint不是购买/穿戴断言 |
| [CDP](../scripts/lib/cdp.cjs) | 本地端点、明确/唯一page选择、受时限与大小约束的求值及连接 | evaluator能运行任意JS；传输层不提供只读权限或游戏规则 |
| [DOM / Inspector](INSPECTORS.md) | scope、唯一性、几何、中心命中、覆盖层线索、CSS/结构比较 | DOM不采完整正文/值；ownership默认unknown；命中观察不是Action派发守卫，结构地址不是item identity |
| [Integration Contract 1](INTEGRATIONS.md) | 审阅本地模块、detect/describe/collect/redact、bounded worker、只读探针约定、可选失败隔离 | collect没有目标参数、动作解析或断言接口；现有SW桥只输出诊断解释，不提供完整游戏语义 |
| [Evidence / 格式](FORMATS.md) | 来源、时间、incident、SHA、部分失败与隐私投影；[离线比较](EVIDENCE_TOOLS.md) | Generic不读取游戏业务状态；complete不是业务结论；Support不能直接复制语义业务数据 |
| [Skill](../.agents/skills/dol-dev-tools-paisley-park/SKILL.md) | 最小充分路由、标准能力优先、直接工具出口、测试环境授权、unknown与Scoped Done | 需要后续增加有限语义目标的选择/暂停/结果判断；不能现在把拟议能力写成可执行指令 |
| [Workshop](WORKSHOP.md) | 目标项目源码→build/deploy→加载身份→同场景复验 | 不提供测试进度重置或游戏业务回滚；不由Tools重写项目发布流程 |

其中Action/Journey的执行实现和失败边界已直接核对源码；既有能力覆盖复用[覆盖表](CAPABILITY_COVERAGE.md)，没有为设计重新跑设备或业务验收。

## 2. 最小能力模型

只保留六项职责，不建大型Agent Framework、独立Gameplay Runner或第二套E2E系统：

| 职责 | 最小输入 / 输出含义 |
| --- | --- |
| 目标与权限范围 | 用户目标、测试目标身份、选定场景、允许动作/副作用、时间/动作/消费边界 |
| 现场语义观察 | 当前Passage/业务地点、打开的Surface及是否阻挡、必要原状态、来源/支持范围/采样身份 |
| 动作映射 | 从语义动作解析到当前真实控件、原行为、前置条件与预期后置条件 |
| 目标驱动决策与重规划 | Agent根据当前事件、可执行选择和目标决定下一步，可处理随机事件、分支、战斗、临时绕路并重规划；现成短路径是可复用手段，不是唯一决策来源 |
| 执行与结果核对 | 复用现有执行器，读取执行前/后原状态，区分命令完成、动作结果与目标完成 |
| 正常变化与危险未知分流 | 正常Gameplay变化重新理解并继续；失去可靠观察、连续结果无法解释、Runtime损坏、存档破坏或游戏外高风险才暂停诊断/请求决定 |

场景解释可表达衣柜/商店/卧室/设置/存档、Passage、modal/drawer/native overlay，以及当前可执行动作。这些是概念词汇，不冻结字段名、枚举、Schema或协议版本。识别到存档页并不意味着获得存档写入权限。

当前框架位置、业务地点与Surface分别记录：页面叫“Wardrobe”不自动证明玩家实际地点，Surface存在也不自动表示阻挡。首次遇到的Passage、Mod选项或路线不自动成为异常：读取现场与原选项，形成带来源的解释，安全可解释时自主行动。某个映射unknown/unsupported不等于整个Goal失败；不从某个CSS类、翻译文本或SW role独立确定事实。

### 语义提供者与事实来源

- 基础DoL语义映射读取所选游戏版本的原场景/状态和原控件；不依赖SW。初版只支持核实过的场景与版本，不以一个全局对象存在就宣称兼容。
- 项目Integration可补充Surface、分类、控件映射及能力解释；SW、其它UI和其它Mod平级可选。不把Adapter match/level作为业务后置条件。
- 同一目标出现冲突解释时用当前原状态和控件重新核实，或选择另一条可解释游戏内路径；不能静默把指定商品换成其它商品。可选增强失败不让Generic Evidence失败，也不禁止借助可靠底层观察继续理解；关键观察持续丢失时才暂停。
- Agent解释目标、事件及选择，自主决定下一步和何时重规划/诊断；业务完成断言由原状态读取器完成，不靠LLM猜测“应该已经穿上了”。

## 3. 与Journey的关系

最高层采用“Goal → Observe → Interpret → Act → Observe Again → Replan”。Goal可以跨越多个Journey，Journey片段失败后也可以重新理解并选择另一条游戏内路径。Journey只是执行手段，记录目标与实际片段关联；不将固定路径成功作为Goal成功条件，也不新增任意JS/循环DSL或另一套点击引擎。

```text
目标：穿上指定服装
  ↓ 读取选定原状态、场景与权限
确定下一步及动作前条件
  ↓ 解析当前控件；不预存未来页面的索引/坐标
Action / 小段Journey：现有wait、click/input、checkpoint
  ↓ 重新读取游戏原状态
目标满足 → 完成
正常事件 / 分支 / 地点或时间变化 → 重新理解、处理、重规划并继续
旧控件已失效 → 不派发旧动作，重新读取和解析新动作
动作结果未知 → 读取实际结果，不盲目重复消费；能解释则重规划
无法安全解释 / 观察丢失 / 破坏存档或游戏外高风险 → 暂停诊断或请求决定
```

**不能把整个“购买→返回→穿戴”一次性编译成无业务断言的静态Journey。** 现有runner只知道动作/wait/checkpoint；若购买后不核对金额和库存便继续，业务失败不会自然形成Journey失败。

初版在每个有业务副作用的动作后结束执行片段、核对后置条件，再决定下一步。稳定且没有中间业务分支的导航可合并成小段。执行、deadline、失败处理、ADB/CDP资源管理仍全部复用现有runner；薄编排只拥有目标、观察引用和控制进度，不重新实现点击/输入/连接。

现有单段120秒/50步不是整个语义目标的预算。还需要目标级总期限、最大派发数与必要消费上限，防止拆成无穷小段绕过限制；具体默认值在首个真实场景核实后选定。只读后置条件允许短时、有上限的轮询，轮询不是业务动作重试。

开发验收模式可以要求固定起点/检查点、可复现路线与失败Evidence；Gameplay以目标结果为主，允许动态路线和正常随机事件，不因原计划未走完判失败。两者共用Semantic Layer、Action、Journey、CDP/ADB、Evidence与Integration，没有独立状态解析器或执行引擎。现有项目smoke/精确identity检查更合适时继续使用，不为形式生成第二份Journey。

## 4. 状态读取边界与保存策略

读取必须由任务按需选择；默认Generic采集和Support保持2.x边界。

| 需要回答的问题 | 最小读取 | 不扩大到 |
| --- | --- | --- |
| 我在哪、还能执行什么 | 当前Passage/业务地点、当前事件的小scope、有限原选择标签及控件状态 | 所有Passage文本、全页遍历、剧情全文 |
| 能否购买指定商品 | 指定商品/变体/目的地、必要库存或容量、原价与货币、按钮状态 | 完整库存、账号、全部玩家变量 |
| 是否真的穿上/脱下 | 目标衣槽当前原穿戴、目标物品定位与相关条件 | 全身体/角色状态、完整存档 |
| 动作有没有推进时间/业务 | 该场景需要的原时间与允许变化、相关数量/金额前后值 | 游戏全历史、任意事件追踪 |
| UI是否正确响应 | 同scope的结构/CSS/画面及原状态后置条件 | 把UI镜像store或Adapter声明当成原业务真相 |

不同版本的原字段、单位、库存目的地与物品实例规则要实证；没有可用来源就unknown，不能填0、把衣服定义当拥有物品、把包装App版本当游戏版本。来自多个异步查询的状态不宣称原子快照；目标身份/场景变化时放弃旧绑定。

内存中的小型前/后观察只是带来源与寿命的证据，不作为下一步的业务真相源；下一步重新读取。重复物品不能仅凭列表索引、显示名称或类型认定实例；先用当前项目可验证的标识/变体和实例绑定，仍有歧义就让目标更具体或停止。

业务值只在显式语义任务内用于判断。默认结果保存断言结果、允许的差值/状态摘要、采样来源/时间与执行记录关联；完整原值、商品自由文本、目标参数和计划可能敏感，保留本地、按需选择，不自动进入Evidence/Support/Issue。即使只保存哈希也不宣称匿名；小值域可被枚举。保留既有采集与完整性状态，另列目标/断言结论，不把业务失败改写成Generic采集失败。

普通存档列表/元数据读取和进入已允许测试存档可用于Gameplay；不为场景理解下载完整存档、不遍历Storage值、不读取云数据。读取/加载不等于删除或覆盖授权，不把启发式redact当成未知数据的安全保证。具体语义制品格式和Schema在代表性样本后再定，不冻结或改Schema 1。

## 5. Action mapping方案与需要补的守卫

映射说明至少回答：动作/参数的意义、支持环境、目标范围、控件定位、原业务行为、前后条件、允许副作用和所需执行方式。这里只定义职责，尚不决定公开函数名或JSON形状。

| 语义动作 | 解析与核对 | 执行与后置验证 |
| --- | --- | --- |
| 打开衣柜/商店 | 根据当前场景选择原导航，事件或路径变化后重新解析；存在唯一真实入口 | 使用原入口；读取实际结果并重新规划；不把Engine跳转/修改位置变量当作实际导航 |
| 切换分类 | 当前真实分类控制器与目标分类唯一匹配 | 原click/input；核对原分类/实际可见列表，不只验证按钮class |
| 穿上/脱下 | 当前物品实例、槽位、操作条件及原控件一致；明确原穿戴基线 | 原业务控件；核对原穿戴与相应库存变化，不能只看图标或卡片 |
| 购买 | 商品/颜色等变体、数量、价格、库存目的地、容量与预算明确 | 一次原购买动作；验证原金额、目标库存/目的地和实际物品，结果不确定不重复购买 |
| 返回/关闭 | 识别当前Surface及原返回语义，区分网页返回与Android back | 原关闭/返回动作；验证Surface/页面；不把所有浮层都当作可安全关闭 |

首版优先原可见控件。公开原动作API只有在实际审阅其来源、副作用和行为等价性后才作为显式映射；不复制购买逻辑、不写money/worn/inventory、不猜私有函数。测试夹具可能使用直接赋值或Engine跳转准备现场，这类准备必须单列授权/证明，不能迁移为正常Gameplay动作。

### 当前动作安全缺口

2.0.1 `web-click`只做唯一HTMLElement、连接、disabled/inert和基础可见性检查，然后DOM `click()`；未把`elementFromPoint`遮挡或业务语义绑定放进派发条件。因此仅在执行片段前调用hitboxes仍存在检查与点击间漂移，不能通过第一阶段的“有遮挡则不派发”验收。

建议在**共享Action派发边界**增加一个仅供明确语义任务选择的有限守卫路径：尽量在同一个页面同步求值内重新核对场景、目标业务绑定、连接/可操作性及中心命中，再调用原控件。复用当前Inspector的观察方法和Action执行链，不新建点击器、不改变2.x普通调用的含义。精确接口/有限条件集合属于后续实现设计；不开放任意用户JS断言DSL。

中心命中只证明该采样点，不等于完整触摸区域/用户手势。页面要求trusted输入或特殊事件序列时，声明标准DOM click不支持；可按现有直接工具出口使用已验证的Playwright/CDP输入路径，明确记录来源与证明边界，不静默force、点父节点或改用固定坐标。没有核实的执行方式就unsupported。

CDP超时/断链时无法保证取消已派发JS。动作回执与语义后置条件必须分开，不能声称exactly-once、远端回滚或暂停瞬间已取消。页内同步守卫降低已知漂移风险，也不保证所有异步业务、系统焦点和跨进程竞态消失。

## 6. Integration提供项目语义

Generic保持独立；基础DoL语义与项目增强是显式选择的可选能力。建议将DoL映射与SW增强分别放在独立Integration目录，实际结构以首个薄实现为准；本轮不创建占位目录或注册中心。

提供者负责只读的场景/状态解释、动作描述与定位映射、后置条件数据来源；**不负责直接执行动作、持有业务状态、回滚存档或决定授权**。执行与消费检查留在共享Action/Journey及语义编排边界。

复用Contract 1的模块来源审阅、能力检测、探针限制、故障隔离、显式加载与输出投影方法。但其当前接口没有目标请求上下文，不足以按某一商品/实例做观察/解析。需要一个小的、单独协商的语义提供者接口，传入经校验的有限任务参数；不将动作写入现有collect，也不把旧Contract的capabilities标签冒充完整语义API。

现有诊断Contract 1保持兼容，新语义支持单独声明/检测。缺失、版本未知、断言来源不可用或结果有歧义时，相应语义动作unsupported/blocked；Generic仍可用于诊断。经过截断、过滤或面向分享的摘要不能重新作为派发依据；必须使用当前任务经过验证的最小原观察。

Worker不是权限沙箱，reviewed local code原则继续成立；暴露evaluate也不是只读权限边界。未知第三方Integration不自动下载/执行，也不从网页或Mod文本中的“指令”获得执行权限。

## 7. Gameplay自治、硬边界与真正异常

语义目标开始时绑定当前设备、package、Android user、WebView目标与已确认测试进度；校验授权范围。过去获准使用某App可复用该授权，但历史设备/PID/socket/进度身份仍需现场重新核对，不擅自把当前连接当作新的隔离环境。

正常Gameplay默认自治：移动、普通对话/剧情分支、随机事件、战斗、买卖、穿脱、睡觉、时间推进、菜单/Overlay、普通设置、测试App重启/重载和路线调整，由Agent根据目标与当前状态自主选择、核对并继续。购买数量/消费预算尊重明确目标，但不能因为会改变游戏状态或出现新Passage就询问。指定物品身份不得擅自替换；普通事件的选项可自主决定，真正影响用户目标的关键歧义才询问。

**删除已有存档、覆盖已有存档默认禁止**；未获得相应明确授权，不执行对应写入，也不点击破坏确认。存档页面、列表读取和加载已允许测试档本身不禁止。真实账号/凭据、游戏外系统、清除真实数据/删除Mod以及无法确定的明显不可逆破坏仍需要已有相应授权或用户决定。正常游戏时间和状态变化不能被扩大解释成全面禁写；硬边界是操作审阅/工作流约束，evaluator和Integration不因此成为权限沙箱。

每个目标串行执行，避免多个Agent同时派发冲突动作。发现外部变化时放弃旧绑定、重新观察；能够解释且目标仍成立即可重规划继续，无法确定现场归属或安全继续时才暂停。初版不引入跨进程锁服务；独占约定不是原子事务保证。

执行区分：未派发、已派发等待验证、后置条件满足、后置条件不满足、结果unknown。完成必须有新鲜原状态证据；没有证据不填成功。曾派发而结果未知的购买/穿戴/导航不自动重试；新进程或新会话也不能凭目录名恢复推进。

先区分两条路径：正常事件/首次见到的选项/路径改变，优先观察、理解、自主选择、核对，再回到目标；不自动进入诊断。只有观察丢失、无法确定仍属于游戏、连续多次结果无法解释、DOM/Runtime明显损坏、存档破坏或游戏外高风险等无法安全继续情况才暂停。单个旧selector失效不是全Goal异常，也不能靠盲目重复购买解决unknown。

真正暂停后使用以下恢复路径：

1. 停止新的业务派发；清理自己已知拥有的临时资源，保存失败与派发边界。
2. 用受影响scope的观察、Inspector或已有Evidence回答具体缺口，不默认Full Evidence/Perfetto。
3. 核对环境、Tools、目标项目、第三方或未知归属；缓存Console事件或Adapter解释不能单独升级为新根因。
4. 先前动作结果、当前状态、目标身份、剩余预算与下一步已足以安全判断后，自主恢复并重规划；只有仍缺关键决定时询问。不能因恢复而盲目再次消费或自动修改源码。
5. 无法确认保持paused/unknown；目标确实不支持时明确unsupported。具体状态名称待实现确定，与Evidence complete/partial/failed及产品完成状态分别表示。

原穿戴恢复是新的原游戏动作序列，不是runner资源cleanup。原负载可能涉及多个槽位、互斥服装和库存移动；初例限定可验证的单槽位物品，恢复必须确认初始原穿戴，不能仅把“脱下目标物品”当回到基线。购买消耗不自动撤销；测试重置使用目标项目预先准备的隔离进度流程，绝不自动重载/覆盖真实存档或赋回金额。

## 9. 真正新能力、推进顺序与待核实问题

现有模块继续承担传输、动作、有限Journey、诊断、证据和构建部署。真正需要新增的是：有限语义观察/目标参数、原状态后置条件、目标到真实控件的映射、目标级预算/暂停与执行记录关联，以及共享Action中的语义守卫。设计审计时这些尚未实现；当前源码进展见末尾实施记录，不能把已有购物脚本或裸CDP操作改名为完成3.0。

建议按真实闭环推进，而非预建全部注册框架：

1. 核实一个版本的场景/原状态读取与唯一控件映射；先完成只读理解和打开衣柜，确认基础语义不依赖SW。
2. 同一个薄路径加入单槽位穿戴/恢复、共享守卫与偏离暂停；读写分离和未知结果先成立。
3. 复用同一层加入一次原购买与消费/库存验证，不另建shop runner。
4. 选一个真实开发变更完成前后同场景复验与A—D代表性验收，之后才固化最小接口/制品格式、更新Skill、统一封装3.0。

实施前需现场核实：首个游戏/Loader/包装App与测试进度；当前场景读取入口及单位；商品/服装实例与库存目的地的稳定绑定；原控件是否支持DOM click、是否有trusted要求；导航/购买/穿戴的时间、自动存档与随机副作用；测试基线准备和恢复路径。这些是具体首场景接入条件，不是要求穷举世界。

正常随机事件与临时绕路属于Gameplay，由Agent自主处理后回到目标；不因未预先写路线就判失败。无止境长旅程、破坏已有存档或无法证明恢复的复杂验收衣槽仍超出本轮有限验收边界。彩蛋可在能力成立后作为同一语义入口的一句提示，不单独写自动玩脚本。

**拟议3.0 Done：** 在上述约定真实目标中，Goal→Observe→Interpret→Act→Observe Again→Replan闭环成立，正常事件/绕路可自主处理，真实目标状态证明完成；危险未知进入诊断、未授权删除/覆盖已有存档不执行。A—D通过，Generic/Integration分离、数据权限及失败/资源清理正确，无范围内阻塞缺陷。未验证生态组合另记Coverage，不要求完整通关或自动玩一天。
