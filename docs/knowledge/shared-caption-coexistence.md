# 两个Mod修改同一侧栏锚点，入口仍可共存

2026-10-16，6.0真实兼容调查的负对照。先在ModHub1.5.0、原版优化1.1.1.2上观察实际启动执行，再下载作者当前发布并更新至1.7.0/1.1.1.5，补做有限入口验证。两次结果分开引用。

## 为什么值得检查

原生ModLoader的启动前冲突模拟没有报告资源重叠，但已加载Manifest声明多个Mod修改StoryCaption、overlayReplace等同一目标。源码中的模拟发生在Addon实际修改之前，因此空列表无法证明后续TweeReplacer没有交互。反过来，共享目标声明也不能直接判定兼容失败。

本次只选择ModHub与原版优化的侧栏/菜单入口。它们的StoryCaption规则使用同一个保存按钮结尾锚点；两者都保留该锚点再追加内容。原版优化还用`getModZip("ModHub")`判断是否隐藏备用管理器入口。这个条件只证明包存在，不能代替ModHub初始化成功，因此还需要实际打开管理面板。

## 旧组合的实际执行证据

测试App保留原39个Mod，未禁用或重排其它Mod，不是只装两个Mod的矩阵。使用固定Tools提交`1dd4fdf2e8ca9a5650d501782c77d2ade1902aa9`构建自有临时探针，选择两项资源与两个Mod；方法源码核验、采集容量及停止机制沿用[启动观测实验](../../examples/patch-provenance/README.md)。

取得12项记录：2次选中的do_patch、10次发布，主动过滤7项、容量丢失0项、观察器错误0项。两个Mod都在各自方法前后改变所选资源。原版优化接到的StoryCaption摘要与ModHub输出不同，说明中间存在未采集的修改；不能把过滤后的时间线解释为直接相邻或完整原因图。

最后一次原生发布返回，随后从当前绑定读取的两个资源摘要对应其最终值。方法resolved不证明每条规则命中，发布返回也不代替入口功能验收。

带探针与移除探针后，各执行一次相同16步原生Action/Journey：打开ModHub、进入模组管理，关闭后打开选项和原版优化页，再关闭并回到Start。两次均complete，管理容器和优化控件可见。侧栏ModHub按钮一个，备用提示按钮零个。没有点击设置值、购买或存档按钮。

仅删除本次原ZIP摘要对应的自有探针，重启后确认探针记录/全局均不存在，原顺序与隐藏列表恢复，原方法摘要及所选资源摘要一致。原始记录在本地忽略目录`phase2-shared-*`，汇总断言为`phase2-shared-negative-control-validation-001.json`。

## 可复用判断与未验证范围

遇到共享目标时，先区分声明、原生模拟、实际Addon执行、最终发布和相关功能结果。检查后续锚点是否保留、是否刻意退让，以及真实入口能否使用，再决定是否需要调整兼容方案。当前结果没有依据要求禁用其中一个Mod。

该案例只证明所选菜单入口在两组代表性配置中共存。没有覆盖全部替换规则、所有优化功能、ModHub完整生命周期、购买/存档/剧情、触屏像素命中或其它版本设备。菜单初始化可能有自身状态写入，不能把“未点击设置值”写成“整个App零写入”。

这是一次无冲突对照，未产生原因—修复—共存的真实冲突正例，不能据此宣布6.0兼容修复验收通过。
