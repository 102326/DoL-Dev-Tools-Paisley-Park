# 重建包与加载脚本不同：把隐含构建输入也补齐

修订 2，2026-10-16。来自本轮真实 MapleBirch 消费者维护任务；适用的是这次 LyraMouthCompat051213 0.1.2 的构建，不是通用的哈希差异根因。

## 判断如何修订

最初从 Tools 根目录运行隔离副本的原打包命令，只复制了消费者 TS、Manifest、说明、许可证和原构建/测试脚本。构建和局部测试通过，版本也与设备一致，但 JS 成员 SHA-256 不同。

第一次对照发现 esbuild 输出包含源文件相对路径注释，调用 CWD 改变会改变字节。改为从消费者工程根目录构建后，摘要仍与加载成员不同，因此不能把 CWD 当成全部原因，更不能忽略差异就宣布匹配。此时只是修订 1 的未闭合调查。

随后读取实际加载成员，确认它还多一行顶层 `"use strict";`。原工程的根 `tsconfig.json` 启用 strict，而隔离副本遗漏了该隐含输入。第三个独立副本补齐原 tsconfig、package.json 和锁文件，并从消费者根目录运行原命令，产物才与实际加载成员完全一致。没有删除严格模式、过滤差异或修改源工程来制造通过。

## 本轮实际证据

- TypeScript 5.9.3、esbuild 0.28.2，与目标锁文件一致；使用已有工具链，不把 UI Runtime 打进消费者。
- 新构建的 `mouth-compat.js` 与加载归档成员均为 SHA-256 `fc507845d33c5f1001c9830fe9a17d0b6ff0e9d7e7843fa22ec712fb55d787bb`。
- `boot.json` 成员均为 `704f9111b7e5fe71379b4e8e422b8863b40c1c158b5bbf856fa1fddea7a681c9`。
- 在原生 Android 执行绑定内，注册的 srcfn 与实际 sidebar 缓存函数都匹配新构建中提取的函数摘要；原 showfn 身份保留，mouth.show=true，图片解码为 256×256。已审的路径函数返回正确的已知路径与回退路径。
- 当前实际组合为 MapleBirch 5.4.2、Lyra 0.5.12.13-1.0.1a-1004.1-goose-ucb、UI 2.7.0-rc.1。没有通过升级、重装或改存档让结果匹配；没有据此验证框架 5.4.3。

两次不匹配的构建、原输出与差异均保留。另有两次 CDP 超时，实际检查发现设备睡眠/锁屏；标准 unlock 仅在非安全锁屏条件下完成后，新的同步元数据读取成功。超时没有被归为消费者缺陷，也没有重复派发游戏业务。

## 下次如何用

先核对实际加载目标，再保留原失败并比较差异。必要输入除了源码和显式命令，还可能包含根配置、锁定工具版本、工作目录、环境变量及上级配置。按已证实缺口补齐隔离副本，不先把空白/注释删掉或统一“忽略哈希”。

成员相同不等于整个 ZIP 相同；函数源码相同也不单独证明闭包状态、其它 Mod 或所有业务正确。本次包 ZIP 哈希仍是独立制品身份，没有拿它冒充设备原始 ZIP。真实图像参数读回不是新截图的视觉验收，也没有验证所有脸型、表情或场景。

来源保留在本地忽略目录的 `maple-consumer-build-001/002/003`、`runtime-proof*`、`live-build-diff.txt` 和各输入摘要；不随 Tools 分发。读不到这些文件时，只能引用本页标明范围的摘要，不声称已独立重跑。
