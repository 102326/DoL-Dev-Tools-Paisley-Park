### 方向一：CLI / MCP 双入口，共享核心与状态所有权

以现有 CLI 及共享 GER / Evidence 为起点，研究增加 MCP 入口的实际收益。两个入口调用同一套核心能力、目标绑定、Session / Goal、预算、Memory、Effect Ledger 和 Evidence 语义；不各建一套 Runtime、Store、执行账本或业务状态，也不把它混成独立 DoL CLI 项目。

优先回答：

1. 两种入口怎样共享请求验证、能力发现、有限错误代码/阶段与结果表示，使 Codex 更容易选择工具、定位失败并接续任务？哪些入口适合直接 CLI，哪些任务实际从 MCP 获益？
2. CLI 与 MCP 同时访问原目标或 Session 时，如何沿用一个协调器的派发、预算和 fencing？请求身份、原 nonce/attempt 与回执归属如何保持，避免双重派发或用另一入口结清旧 Unknown？
3. 长任务、断连、取消及重连怎样表达实际执行状态？传输结束不代表远端取消；连接所需的临时状态不能成为另一份业务持久状态。
4. MCP 入口的进程/会话归属和宿主发现需要什么最薄接线？与现有一次性 CLI、已有 stdio 实验比较后，是否确实减少步骤、等待或人工介入？不预定 MCP SDK、协议版本、进程架构或常驻服务方案。

普通 Debug 保留轻量路径，不因新增入口强制进入 GER。受保护业务操作复用 GER 的原结果核对与恢复；游戏事实仍来自 DoL，入口成功或模型叙述不是 Outcome。相关基线见 [Gameplay](../../GAMEPLAY.md)、[PC Runtime](../../PC_RUNTIME.md)及[既有进程实验](../../../experiments/weather-report-20261104/REPORT.md)。

### 方向二：从现有 Contract 1 研究更深的 Integration

当前 [Integration Contract 1](../../INTEGRATIONS.md)的 `describe / detect / collect / redact`、有界 Worker、JSON-only 输出、明确目标/文档及可选失败边界作为对照基线；这些观察接口不自动构成主动操作协议或授权。具体契约怎样演进，要由实测决定。

| 研究优先级 | 对象与目标 | 当前边界 |
| --- | --- | --- |
| 第一层：自有项目 | Soft & Wet / The Hand / Sticky Fingers，先找能改善现场理解、开发诊断或受控操作的真实任务 | 优先次序不代表三者已有完整 API、深度桥或验收结果；需分别确认实际项目接口和任务范围。当前不改这些项目。 |
| 第二层：合作生态 | ModHub 等，围绕与作者协作才有价值的能力研究接口与分工 | 目前只是合作研究目标，没有取得作者合作授权的结论；本次不联系作者、不接入或改动对方项目，不推断私有 API。 |
| 第三层：普通第三方 | 有具体任务和收益时按需研究 | 不承诺通配支持、自动扫描执行、包管理或第三方生命周期接管；实际接入另按来源、权限和任务核对。 |

这些层级只规定研究顺序，不改变现有可选、平级接入原则，也不让 Generic Diagnostics 依赖某个自有 Mod。

观察能力与主动操作能力可以分别研究、分别授权、分别验证：

- 观察研究关注目标项目实际提供的能力/版本、状态解释、来源、文档代次和 Evidence 归属；缺失、未知或失败的可选 Integration 不应抹掉成功的 Generic 采集。Worker 继续不能被当作权限沙箱。
- 操作研究关注是否存在可审查的原入口、明确的数据/任务权限，以及报价/预算、派发、原状态 Outcome、终态回执和恢复。可参考现有 [Project Recipe](../../PROJECT_EXPERIMENTS.md) 与 Action/GER 接缝；不能因 `detect=available`、诊断输出或“自有项目”标签自动获得操作权。
- 各 Mod/Runtime 保有自身业务状态，Gold Experience 消费观察与解释，不复制其内部状态系统。新的观察字段或能力声明不直接成为游戏真相、授权或历史 Effect 的结算依据。
