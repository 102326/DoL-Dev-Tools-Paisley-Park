# Windows 独立模型接手对照

2026-11-26。在一次部署缺少确认、随后源码发生漂移的中性任务中，两位新操作者都验证了页面实际加载的候选，也都保留了部署 Unknown。人工组在第二阶段把工具仓库的 HEAD 填成了构建输入的 HEAD；回执组报告了正确的源码身份。这一次没有显示出稳定的耗时优势。

## 怎么做的

工具源码固定为 `faa627cb6f0cf962892a046f170eae1e973e826e`。通过 Codex 原生独立任务入口启动两个 `gpt-6.1-terra / high` 操作者，均未继承父对话历史；第二个检查点交还各自原会话。两组同时使用共享的合成输入源码、同字节 ZIP、同一探针与预期，两份独立 Chrome Profile、Tab 和回执。各自目录起初具备同种输入、人工交接单及封存记录。没有 E46 游戏输入或设备操作。

人工组按 7.2 式交接单选择工具，使用项目 `pc-bind`、`pc-observe` 和已有研究脚本文本读取帮助。回执组使用同一研究树的 `dev-receipt`。两组都能读取原文件并直接计算摘要。这对比的是两种交接方式，不能从中推导两个发行版本的综合性能。

每组交班前派发一次候选，原 Tab 刷新一次，交班时故意不给部署 ACK。首次准备曾在新页面就绪前调用同步检查而读到 `cdp-unavailable`，该轮未交给模型。准备脚本随后先等待新 loader 和页面实际显示的候选值，才开放两组交接。操作者获准只读比对、显式重绑及写新证据。两组完成首次判断后，协调方只编辑一次共享的受跟踪输入，保持 Git HEAD、制品和文档不变。

## 实际结果

| 检查点 | 人工交接 | 回执交接 |
| --- | --- | --- |
| 第一次接手 | 87.5 秒，6 次 Node 调用，2 次 resolver 失败；原 Tab 上建立新绑定，ZIP、实载脚本和页面均核对成功 | 102.4 秒，8 次 Node 调用，1 次 resolver 失败；读到文档变化，重绑并留下实载和行为回执 |
| 同 HEAD 源码编辑后 | 17.5 秒，2 次 Node 调用，均成功；重新观察到旧脚本、旧行为，拒绝把旧 PASS 用于新输入。首答填错 Git 根 | 15.0 秒，1 次 Node 调用成功；`resume` 读到当前源码需要重建、原文档脚本仍匹配。另用 Git 和文件摘要核对输入，明确行为通过是历史结果 |
| 部署 | 保留 Unknown，无补发 | 保留 Unknown，无补发 |

耗时从各自首个可记录操作到写出结论，不含精确送达前后的全部时间。人工组从首次计量的 Node 操作开始，回执组从首次记录时钟开始。Node 数来自本地进程记录，不等于全部操作数。例如人工组另用 Python 读 ZIP，回执组另用了 PowerShell、Git 和文件摘要。人工组第二阶段重新采了行为，回执组复用了同文档的有效证据。两者的操作成本也包含这些选择。

两组最初均调用了用户目录的安装版 resolver，校验失败。协调方向两组同时给出了工作树 resolver 的准确位置，均定位到正确 CLI 并继续。人工组补充结果另存，首次未完成记录保留。验后还专门提示人工组核对 Git 根，才得到正确的源码 HEAD；这次提示和改正单列，未回填原计时或原评分。

## 复跑与交班

从研究仓库运行以下命令。指定新输出目录、Chrome 和 Python 的绝对路径，以及两个空闲回环端口。父目录需已存在。脚本创建自有 Git 输入、候选包、两份人工交接单和两份研发回执。

```text
node experiments/wonder-of-u/windows-model-sample.cjs NEW_OUTPUT CHROME PYTHON PORT_A PORT_B
```

等待 `ready.json`。分别给无共享对话历史的操作者分配 `manual/manual.json` 与 `receipt/receipt/handoff.json`，提供同一工作树 resolver 路径。要求两组检查源码、ZIP、当前文档脚本、探针和缺失的部署确认，仅在本组写新证据。Node 命令加 `-r ABS_ARM_METER_CJS` 可记录进程次数和退出码，Shell、Git 等另计。收齐独立判断后在输出根独占新建空文件 `change-source`，见到 `changed.json` 后向两组给出同一条“请重核当前输入”指令。结束时新建空文件 `stop`，核对 `closed.json`。运行期间需要保持样例进程存活；30 分钟自动关闭。重跑会产生新的目标和源码仓库身份。

对应的通用改动集中在[研发回执指南](../../docs/DEV_RECEIPT.md)，交接时给出项目 resolver 和构建输入根。独立 Android 壳的[真机检查清单和采证命令](android-shell/README.md#构建选择设备和发布到私有目录)已经准备好；本轮只验证本地输出契约，未接触平板。

**给 Gemini 的短交接。** 在 Windows 上，两个无共享历史的新模型会话都从缺少部署确认的同一中性候选接手，验到当前文档的候选脚本与预期页面；源码漂移后都拒绝沿用旧 PASS，均无重放。人工组首答误填工具仓库 HEAD，经提示才更正。样本只有一对，且两组都收到一次 resolver 路径提示，没有依据宣称回执更快或模型更聪明。下次交接直接给项目 resolver 位置，并从配方的源码根核对提交。
